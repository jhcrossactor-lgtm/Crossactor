## 3. 要件と実際の能力のギャップ（2件・要判断）

### G-1｜Slackには「未読」が存在しない

Slack MCPは既読/未読フラグを返さない。`slack_read_channel` は時系列で履歴を返すだけだ。
要件の「未読要約」をSlackでそのまま実装することは**できない**。

**代替案（推奨）：ウォーターマーク方式**
- 最終チェック時刻を `communications/secretary/state.json` に保存
- 次回はその時刻以降の新着メッセージのみを対象にする

**副作用**：ほせもやんがSlackアプリで既に読んだメッセージも「新着」として出る。
→ 対象チャンネルを絞れば実害は小さい。絞り込み方針は §9 Q1 で確認する。

### G-2｜Gmailの検索結果は「古い方から5件」しか返らない

`search_threads` の仕様に明記がある — 各スレッドの**最も古い約5件のプレビューのみ**を返し、
それより新しいメッセージは含まれず、**省略された印すら出ない**。

これを要約にそのまま使うと、**最新のやり取りを落とした嘘の要約**が出る。秘書としては致命的だ。

**対策：必ず2段構えにする**
1. `search_threads` で対象スレッドを**絞り込むだけ**
2. 各スレッドを `get_thread` で**全文取り直してから**要約する

**副作用**：トークン消費が増える。→ 1回あたりの処理上限を設ける（§5 既定20スレッド）。

## 4. 承認ゲート設計

操作を危険度で3段階に分ける。**判断に迷ったら必ず上の段に倒す。**

| 段階 | 内容 | 承認 | 該当操作 |
|---|---|---|---|
| **L0** | 読み取りのみ。外部に何も残らない | 不要 | Gmail検索・スレッド取得／Slack履歴・検索／カレンダー取得・空き時間提案 |
| **L1** | 下書き作成。**相手には届かない** | 不要（ただし作成内容を必ず報告） | `create_draft`（Gmail）／`slack_send_message_draft`（Slack） |
| **L2** | 外部に影響が出る。取り消しが困難 | **1件ずつ明示承認** | Slack送信・予約送信／カレンダー作成・更新・削除・出欠回答／Gmailラベル変更・ゴミ箱 |

### ハードルール

1. **`slack_send_message` は秘書の通常フローから除外する。**
   既定は「下書きを作る → ほせもやんがSlack上で確認して自分で送る」。
   秘書が送信ツールを呼ぶのは、ほせもやんが**そのメッセージについて**明示許可した場合のみ。
2. **Gmailは下書き止まりが構造的な上限。** 送信ツールが無いので、それ以上は不可能。
3. **カレンダー書き込みは「提案 → 承認 → 実行」の3ステップ固定。** 提案なしにいきなり `create_event` を呼ばない。
4. **破壊的操作（ゴミ箱・削除・アーカイブ）は既定で禁止。** 許可するかは §9 Q6。
5. 承認は「その時のメッセージでの明示的な許可」を要する（AGENTS.md 行動制約）。
   過去の承認を次回に持ち越さない。

## 5. 機能設計

### F-1｜未読要約

| | |
|---|---|
| 入力 | 最終チェック時刻（state.json） |
| 処理 | Gmail: `search_threads`（`is:unread in:inbox`）→ **各スレッドを `get_thread` で全文取得** → 要約<br>Slack: 対象チャンネルを `slack_read_channel` でウォーターマーク以降取得 → 要約 |
| 出力 | 差出人 / 件名 / 3行要約 / 緊急度（高・中・低）/ 要返信フラグ |
| 上限 | 既定 Gmail 20スレッド・Slack 10チャンネル（トークン暴走防止） |
| 危険度 | **L0** |

### F-2｜返信ドラフト作成

| | |
|---|---|
| 入力 | F-1で「要返信」と判定されたもの、またはほせもやんの指定 |
| 処理 | スレッド全文を読む → 返信案を生成 → **ほせもやんに本文を提示** → 承認後に下書き作成 |
| 出力 | Gmail: `create_draft`（`replyToMessageId` 付き）／Slack: `slack_send_message_draft` |
| 注意 | Slackは**1チャンネル1下書き**の制約あり。複数必要な場合の扱いは §9 Q4 |
| 危険度 | **L1**（下書き作成は届かないので送信ではない。ただし本文は必ず事前提示する） |

### F-3｜タスク抽出

| | |
|---|---|
| 入力 | F-1で読んだ全メール・メッセージ |
| 処理 | 依頼・期限・約束を抽出。「誰が・何を・いつまでに」の3点が揃うものだけをタスク化 |
| 出力 | ブリーフ内のタスク表。期限順にソート。**出典（メール/メッセージへのリンク）を必ず付ける** |
| 注意 | 推測でタスクを作らない。3点が欠けるものは「要確認」として別枠に出す |
| 危険度 | **L0** |

### F-4｜予定確認

| | |
|---|---|
| 入力 | 対象日（既定：当日＋翌営業日） |
| 処理 | `list_events` で取得。F-3のタスクと突き合わせ、**予定とタスクの衝突**を検出 |
| 出力 | 時刻 / 件名 / 場所 / 参加者 / 準備物（本文から抽出） |
| 危険度 | **L0**（予定の作成・変更は L2 として分離） |

## 6. 出力フォーマット（秘書ブリーフ）

保存先：`communications/secretary/YYYY-MM-DD.md`

```markdown
# 秘書ブリーフ 2026-09-16（朝）

## 1. 今日の予定
| 時刻 | 件名 | 場所 | 準備物 |

## 2. 要対応（期限順）
| 期限 | タスク | 出典 |

## 3. 未読サマリ
### Gmail（n件）
### Slack（n件）

## 4. 作成した下書き（要確認・未送信）
| 宛先 | 件名/チャンネル | 確認先リンク |

## 5. 承認待ちアクション（L2）
| # | 実行したい操作 | 理由 |

```

AGENTS.md の日次オペレーション（朝＝タスクリスト提出／夕方＝報告）にそのまま乗る形にしてある。

## 7. 構成（2フェーズ）

AGENTS.md 運用ルール「ルーティンタスクはClaude Codeで初回構築→動作確認後にCLI化」に従う。

### Phase 1：Claude Codeスキルとして構築（実装済み）

```
.claude/skills/secretary/SKILL.md      # 手順・承認ゲート・出力フォーマット
communications/secretary/config.json   # 対象チャンネル・カレンダー・上限（versioned）
communications/secretary/state.json    # 最終チェック時刻・処理済みID（gitignore）
communications/secretary/YYYY-MM-DD.md # 日次ブリーフ
```

設定と状態は分離した。`config.json` はレビュー対象なのでコミットし、
毎回書き換わる `state.json` はコミットしない（差分ノイズを避ける）。

- 起動：手動（「秘書」と言う）／Routineで毎朝
- ここで**精度と承認フローを固めきる**。CLI化はその後

### Phase 2：CLI化

移す対象と残す対象を分ける。

| 処理 | 行き先 | 理由 |
|---|---|---|
| 取得・整形・状態管理・重複除去 | `scripts/secretary`（CLI） | 決定論的。LLM不要。毎回トークンを払う価値がない |
| 要約・ドラフト生成・タスク抽出・緊急度判定 | Claude Code側に残す | LLM判断が本体 |
| 承認ゲート | Claude Code側に残す | 対話が必須 |

AGENTS.md「MCP接続は常時コンテキストコストを払う価値があるかで判断」に沿った切り分けだ。

## 8. 状態管理

**`config.json`**（versioned）— 対象チャンネル・カレンダー・Gmailクエリ・上限・許可フラグ
**`state.json`**（gitignore）— 実行状態のみ

```json
{
  "version": 1,
  "last_check": { "gmail": "2026-09-16T08:00:00+09:00", "slack": "2026-09-16T08:00:00+09:00" },
  "processed": { "gmail_thread_ids": [], "slack_message_ts": [] }
}
```

`processed` は各1000件で古い方から切り捨てる。

**秘密情報は書かない。** アクセストークン・パスワードの類は一切保存しない（認証はMCP側が保持する）。
メール本文もここには残さない。ブリーフ側にのみ要約を書く。

## 10. Phase 1ではやらないこと（明示的スコープ外）

- 自動送信（**恒久的に禁止**）
- 複数ワークスペース・複数アカウント
- 添付ファイルの中身の解析
- 自動ラベル付け・自動アーカイブ
- 会議の自動調整・自動返信

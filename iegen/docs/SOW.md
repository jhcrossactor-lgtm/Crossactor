# SOW：木造戸建てプラン自動作成システム（仮称 IeGen）

版：v0.9（2026-09-15）／ 作成：Crossactor

---

## 1. 目的

敷地条件（形状・道路・用途地域等）を入力すると、法規に適合した木造2〜3階建て戸建ての間取り案を複数自動生成し、根拠条文付きのチェック結果とともに出力する。設計者（ほせもやん）の計画思想を持つエージェントが案を評価・改善する。

## 2. スコープ

| 項目 | 対象 | 対象外（v1） |
|---|---|---|
| 構造 | 木造在来（900モジュール） | RC・S造、2×4 |
| 階数 | 3階建て（v1）→ 2階建て（v2） | 平屋、地下 |
| 敷地 | v1：60〜70㎡中心（将来〜40坪）、整形・旗竿・角地 | 大規模・高低差大の敷地 |
| 用途 | 建売住宅（専用住宅）、駐車場1台 | 注文住宅、併用住宅、二世帯（v2） |
| 地域 | 大阪府下共通（市は差分管理） | 他府県 |
| 法規 | 基準法・施行令・告示・府条例・市条例・消防法（住警器等） | 確認申請図書の完成 |
| 構造 | 壁量・4分割法の簡易チェック | 許容応力度計算（3階建ては外部連携の前提で「要計算」表示） |

## 3. 設計思想（コア原則）

1. **LLMは提案、決定論コードが判定**：間取り生成はAI、法規・寸法チェックはPythonルールエンジン。LLMに合否判定をさせない。
2. **全判定に条文ID**：チェック結果は必ず「法令名・条・項・号＋取得日」を付す。根拠なき判定は「要確認」扱い。
3. **グリッド思考**：900mmグリッド上（モジュールは設定値として持ち、将来のハイツ・マンション対応時に切替可能にする）の矩形配置問題として扱い、構造（通し柱・上下階の壁線一致）を生成段階で拘束する。
4. **Webを積極的に参照し、アレンジして使う**：建売は敷地条件が近ければ間取りが収束するため、Web上の事例を大量に収集する。保存は「間口×奥行×道路方位×階数→ゾーニング・動線・水回り位置」の特徴量＋出典URL＋取得日とし、生成時は必ずアレンジして使う（図面そのものは複製しない）。自社実績50件は品質基準（正解データ）として使う。
5. **Claude Codeで初回構築→動作確認後CLI化**。

## 4. システム構成

```
入力（敷地DXF/PDF・住所・要望）
  ↓
[1] 敷地解析 ─ 形状・接道・方位・用途地域・防火指定・高度地区
  ↓
[2] 法規ボリューム ─ 建蔽/容積・斜線（道路/隣地/北側）・高度・日影 → 建築可能包絡
  ↓
[3] ゾーニング ─ パターンDBから類似敷地を検索 → LDK/水回り/階段位置の候補
  ↓
[4] 間取り生成 ─ グリッド配置ソルバ＋LLM（設計者エージェント）で複数案
  ↓
[5] 法規・品質チェック ─ ルールエンジン（条文ID付き）
  ↓ NG → [4]へ差し戻し（最大N回ループ）
[6] 評価 ─ 設計者エージェントが採点・講評
  ↓
出力（平面図PDF/DXF・面積表・チェックリストPDF）
```

## 6. 法令参照の設計

### 6.1 ソースと接続

| 優先 | ソース | 接続方法 | 用途 |
|---|---|---|---|
| 1 | Obsidian Vault | Claude Code既存接続を利用（下記6.3の設計に従い、実行時に接続） | 設計者の注釈付き条文・実務メモ |
| 2 | e-Gov法令API | HTTP取得→`law/cache`に保存（取得日記録） | 基準法・施行令・告示・消防法の原文、改正追従 |
| 3 | 大阪府条例 質疑応答集 | NotebookLM／Google Driveから取込 → `law/osaka/qa/` | 府下の運用解釈（v1の主軸） |
| 4 | 府条例解説・特定行政庁取扱い | Google Drive既存PDF（下記）を取込 | 条文解釈・図解 |
| 5 | 自治体サイト | `arch-reg-sync`スキル | 市独自条例・高度地区・日影の差分 |

Google Drive上で確認済みの資料：
- 大阪府建築基準法施行条例 解説（osaka_pref_ordinance.pdf）
- 大阪市建築基準法取扱い（令和3年11月改訂、分冊PDF）
- 各市の開発・技術基準（摂津・守口・堺）、行政調査まとめ（門真・寝屋川）
- 建築基準法及び同大阪府条例質疑応答集（改訂6版・平成23年、105頁）：ユーザー提供PDFで取込済み

### 6.1.1 質疑応答集の取込

- 目次から全324項目を索引化済み（`law/osaka/qa/qa_index.json`：ID・章・根拠条文・頁・v1対象フラグ）
- v1対象：戸建て3階建てに関係する142項目（車庫の延焼ライン、採光、直通階段、非常用進入口、階段・手すり、接道、容積・特定道路、道路/隣地/北側斜線、日影、面積・高さ算定、小屋裏物置、シックハウス）
- 本文は項目単位に分割し `qa/<ID>.md` として保存。rules/の各ルールから `qa_ref` で参照
- **注意：改訂6版は2011年版。** 大阪市取扱い（令和3年）は改訂7版を参照しており、6版以降の法改正（2018〜2025年の採光・防火・4号特例縮小・省エネ等）は反映されていない。e-Gov原文と矛盾する項目は `stale: true` とし、原文を優先。7版を正とする

### 6.1.2 改訂7版の取込（Claude Codeで実施）

- 所在：Google Drive「建築基準法及び同大阪府条例＆質疑応答集改定7版.pdf」（約63MB）
- Driveの本文プレビューが空のため、スキャン画像PDF（文字データなし）の可能性が高い
- 手順：①Google Drive for desktop等でローカル取得 → ②文字データ有無を確認、なければOCR（日本語） → ③目次から項目索引を作成 → ④6版索引と突合し、新設・削除・変更項目を一覧化 → ⑤7版を正、6版は差分確認用に保持
- OCR誤読対策：数値・条番号は原本画像と照合するチェックを入れる

### 6.2 解釈の優先順位（大阪市取扱いの記載に準拠）

1. 建築基準法共通取扱い集（近畿建築行政会議）
2. 特定行政庁の取扱い（例：大阪市建築基準法取扱い）
3. 建築基準法及び同大阪府条例質疑応答集（大阪府内建築行政連絡協議会）
4. 建築物の防火避難規定の解説／基準総則・集団規定の適用事例（日本建築行政会議）

ルールYAMLには `source`（上記の番号・頁）を持たせ、解釈が競合した場合は上位を採用する。

### 6.3 市の扱い

v1は大阪府下共通で設計し、市は選択しない。ただし府条例解説のとおり、市町村条例が同一事項を定める場合はその市域で府条例が適用されないため、`law/municipal/<市>.yaml` に差分（独自条例・高度地区・日影）だけを持つ構造にしておく。

### 6.4 Obsidian接続設計（実行時に接続）

- `law/obsidian_link.md` にVaultルートと対象フォルダを記載（Claude Code実行時に設定）
- 読込ルール：ノートのfrontmatterに `law_id`（e-Gov法令ID）・`article`（条番号）があれば `rules/` の同条文と紐付け
- 役割：条文原文はe-Gov、実務解釈・注釈はObsidianを正とする
- 未接続時はe-Gov＋質疑応答集のみで動作（フォールバック）

### v1で実装するルール（主要）

- 建蔽率・容積率（法52・53、角地・準防火地域の準耐火緩和、車庫・ロフト等の不算入）
- 道路斜線・隣地斜線・北側斜線（法56）、高度地区（都市計画）、日影（法56の2、条例）
- 接道（法43）、府条例の路地状敷地規定
- 採光・換気（法28、令19・20）、居室天井高（令21）
- 階段寸法（令23〜25）
- 防火・準防火地域の構造制限（法61、令136の2）、3階建ての非常用進入口（令126の6）
- 内装制限（火気使用室）
- 24時間換気（シックハウス、令20の8）
- 壁量・4分割法（令46、2025年改正後基準）、省エネ基準適合（2025年4月義務化）
- 住宅用火災警報器（消防法9の2、市火災予防条例）

※条文番号・改正内容は実装時にe-Gov原文で全件照合する（本表は計画用の見出し）。

## 7. 設計者エージェント（hose-planner）の作り方

1. **ヒアリング**：`grilling`スキルで計画思想を30問程度で抽出（玄関位置の決め方、水回り集約、階段位置、収納率、南面の使い方、3階建ての縦動線 等）
2. **実績解析**：過去プラン50件を特徴量化し、ヒアリング内容と矛盾がないか照合
3. **明文化**：`principles.md`（思想）／`dos_donts.md`（禁則）／`scoring.yaml`（評価重み）
4. **校正**：エージェントの講評と本人の講評を並べ、一致率が上がるまで修正

## 8.5 Web事例収集パイプライン

1. 収集：画像検索・ポータルサイトのスクリーンショットを `patterns/inbox/` に保存（出典URL・取得日をファイル名かメモに記録）
2. 解析：Claude Codeで一括読取 → 寸法・部屋配置・水回り・階段位置を特徴量化
3. 選別：自社実績と照合し、品質の低い事例を除外（階段幅不足・採光不足等）
4. 保管：画像は社内の解析用途に限定し、外部公開・再配布はしない
5. 月次で件数・敷地タイプの偏りをレポート

根拠：著作権法30条の4（情報解析のための複製）。ボットによる大量自動アクセスは利用規約上のリスクが高いため行わない。

## 10. リスク・前提

| リスク | 対策 |
|---|---|
| 法規判定の誤り | 条文ID必須、golden testで回帰確認、最終判断は建築士 |
| 法改正追従漏れ | e-Gov取得日管理、月次で差分チェック |
| Web事例の権利・規約 | 手動スクショ＋解析用途限定（著作権法30条の4）、画像の外部公開なし、自動クローラーは使わない |
| 生成案がWeb事例に似すぎる | 類似度チェックを入れ、閾値超えは再生成 |
| 3階建ての構造 | v1は「許容応力度計算要」を表示するのみ |
| 生成案が実務水準に届かない | 自社実績を学習の主軸に、設計者エージェントで評価 |

## 10.5 確定事項

- モジュール：900mm
- 企画条件：間取り重視。駐車場は1台固定。販売価格帯は考慮しない
- 出力：v1はPDF＋DXF。JWW直接出力はv2で検討（JW_CAD外部変形経由、または既存JWWライブラリの書込対応を調査）。当面はDXFをJW_CADで開いてJWW保存
- 地域：大阪府下共通。府条例質疑応答集を解釈の主軸とする
- 対象：木造戸建てから開始（ハイツ・マンションは別フェーズ）

## 10.6 v1プラン条件（木造3階建て・建売）

| 項目 | 条件 |
|---|---|
| 建物間口（短手） | 4,500（5P）が基本 |
| 敷地 | 60〜70㎡ |
| 延床面積 | 100〜105㎡目安（駐車場・バルコニー除く、前後可） |
| 間取り | 敷地に余裕があれば4LDK |
| 1階 | ビルトイン駐車場1台（車の建物外はみ出し可）、居室1、トイレ |
| 2階 | LDK 16帖以上、トイレ、余裕があれば洗面脱衣・浴室 |
| 3階 | 洋室3室 |
| 洗面脱衣／浴室 | 各1,800×1,800 |
| トイレ | 900×1,350 または 900×1,500（取れれば900×1,800） |
| 階段 | 900×2,700 内、または 1,800×1,800 のU字折返し |
| 帖換算 | 1帖＝900×1,800＝1.62㎡ |

### 生成時の判定目安（要検証）

- 2階に水回りを載せる条件：LDK 26.0＋階段2.43＋トイレ1.22＋洗面3.24＋浴室3.24 ≒ 36.1㎡ → 間口4,500なら奥行8,100（9P）以上が目安。未満なら水回りは1階へ
- 容積率がボトルネックになりやすい：延床105㎡／敷地65㎡ ≒ 162%。指定容積率・前面道路幅員による低減で不足する場合は延床目標を自動で下げる（駐車場の1/5不算入を考慮）
- 3階建ては防火・準防火地域の構造制限、非常用進入口、高さ・斜線を優先チェック
